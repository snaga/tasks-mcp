# タスクドメイン & ガードレール層 (`src/task`)

## モジュール概要
- **モジュール名**: `task` (タスクドメイン & ガードレール層)
- **レイヤー**: ドメイン層 / ストレージ層

## 責務 (Responsibility)
1. **タスクのライフサイクル管理**:
   - 初期リストの順序付き登録、状態遷移（`pending` -> `in_progress` -> `completed` / `failed` -> `blocked`）、履歴メモの追記。
2. **厳格な一直線（リニア）実行の強制 & ガードレール**:
   - 暗黙的先行依存（インデックス $N$ の着手には $0 \le i < N$ の全完了が必須）によるタスクスキップの物理的遮断。
   - 単一アクティブ制約（システム全体で同時に `in_progress` になれるタスクは常に1件のみ）。
   - サーキットブレーカー（同一タスクが3回失敗した時点で自動的に `blocked` へ遷移させ、実行を中断して人間の介入を要請）。
3. **安全な永続化 & 監査ログ**:
   - クラッシュ耐性を備えたローカル JSON へのアトミック書き込み（Write-Replace）。
   - すべてのツール呼び出し、引数、所要時間、制約違反詳細を記録する追記専用 JSONL 監査ログ。

## 依存制約 (Dependency Rules)
- **プロトコル層への逆依存厳禁**:
  - `src/mcp` 等のプロトコルハンドラー層への依存は固く禁止されています。
  - 本モジュールはプロトコル非依存の純粋な Rust ロジックとして独立しており、将来 MCP 以外のインターフェース（CLI ツールや HTTP API）へ拡張・再利用する場合でもコード変更なしで動作します。
- **許可される依存関係**:
  - 内部モジュール: `src/error` (エラー定義) のみ
  - 外部クレート: `chrono`, `serde`, `serde_json`, `tempfile`, `anyhow`

## 技術選定理由 (Why)
- **「道具ではなくハーネス（Harness-as-Guardrail）」**:
  - AI エージェント（LLM）の自律的判断や「順番を守って」というプロンプトへの善意の解釈に頼らず、サーバー側の検証エンジンが物理的な制約として振る舞うことで、モデルのサボり・飛び越し・迷走を100%防止します。
- **Write-Replace アトミック書き込み**:
  - 一時ファイル（`NamedTempFile`）に書き出し、`flush` 完了後に同一ファイルシステム上で `rename`（置換）することで、プロセスの突然のキルや電源断が発生してもファイル破損（中途半端な空ファイルや不完全なJSON）をゼロにします。
- **追記専用（Append-Only）JSONL 監査ログ**:
  - エージェントの挙動、実行時間、ガードレール違反の履歴を即時フラッシュ追記し、後からの行動分析、Git 差分追跡、再現検証を容易にします。
