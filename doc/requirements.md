# 要件定義書 (requirements.md)

## 概要

`tasks-mcp` は、自律型 AI コーディングエージェントのための**ガードレール型タスク管理 MCP (Model Context Protocol) サーバー**である。
AI モデルの知能や自己管理能力に過度に依存せず、外部環境（ハーネス）側で状態や制約を決定論的に担保する。
本システムは、タスクリストを**分岐やスキップのない厳格な一直線のシーケンシャルパイプライン**として扱い、先行タスクの完了を後続タスク着手の暗黙前提として強制する。
これにより、モデルの迷子（コンテキストドリフト）、タスク飛ばし、サボりを根本から防ぎ、軽量・低コストモデルでも高いタスク完遂率を実現する。

## 前提条件

- **MCP stdio クライアント**: Cursor、Claude Desktop、Antigravity、自作エージェント等の MCP (Model Context Protocol) stdio トランスポートに対応したクライアントから起動・接続されること。
- **ファイルシステムアクセス**: 実行対象プロジェクトのルートディレクトリに対して、読み込みおよび書き込み権限（`.agent/tasks.json` の作成・更新）を有していること。
- **シングルプロセス実行**: 原則として単一の MCP クライアントセッションからプロセスが起動され、同一プロジェクトに対する並行書き込み競合は発生しない前提であること。

## 制約条件

- **厳格な一直線リニア実行 (No Branching / No Skipping)**: タスクはリストの配列順に1本道で実行されなければならず、分岐・並列実行・タスクのスキップ（飛び越し）は一切許容されない。
- **暗黙的先行依存の強制**: タスク $N+1$ の着手前提は直前のタスク $N$ の完了（`completed`）であり、サーバー側ガードレールでこれを強制しなければならない。
- **シングルアクティブ制約**: 同時に `in_progress`（進行中）にできるタスクは常に1つのみでなければならない。
- **サーキットブレーカー（リトライ上限3回と実行中断）**: 同一タスクの失敗は最大3回までとし、3回到達時はリストの実行を自動中断（Blocked）して人間の判断へ委託しなければならない。
- **stdio 通信の整合性**: JSON-RPC 通信を行う標準出力（stdout）へのログ出力は厳禁とし、すべての内部ログは標準エラー出力（stderr）に限定しなければならない。
- **ゼロ外部依存・単一バイナリ**: 外部 DB サーバーや言語ランタイム（Node.js, Python）を必要とせず、Rust 製の単一バイナリとしてミリ秒未満で起動しなければならない。

## 要件

### 要件カテゴリA: タスク初期化 & 順序管理 (Initialization & Sequential Pipeline)

- 要件 A-1: 順序付きタスクリストの初期登録
  - ユーザーストーリー
    - 私は AI エージェントとして、達成すべきゴールと順序立てたサブタスク一覧を登録したい。なぜなら、以降の作業を一貫した1本道の順序で迷わず実行するためだ。
  - 受け入れ基準
    - ［Event-driven］クライアントが `init_task_list` ツールをタスクリスト（ID、タイトル、説明の配列）とともに呼び出したとき、システムはタスクの配列順序を厳格な実行順序として受け付け、初期状態 `pending` としてストレージに保存しなければならない。
    - ［Unwanted-behavior］クライアントが空のタスクリストまたは重複したIDを含むリストを送信したとき、システムは明確なバリデーションエラーを返し、初期化を拒否しなければならない。

- 要件 A-2: 順序変更や割り込みの遮断
  - ユーザーストーリー
    - 私はプロジェクト管理者として、エージェントが実行途中でタスク順序を勝手に改変したり割り込みタスクを挿入するのを防ぎたい。なぜなら、あらかじめ合意した計画の決定論的な完遂を保証するためだ。
  - 受け入れ基準
    - ［Ubiquitous］システムは、一度初期化されたタスクリストの順序変更、途中挿入、削除のAPIを提供してはならず、初期化時の順序を不変（Immutable Order）として保持しなければならない。

### 要件カテゴリB: ガードレール制約 & 実行制御 (Guardrails & Execution Control)

- 要件 B-1: 現在着手すべき単一タスクの取得
  - ユーザーストーリー
    - 私は AI エージェントとして、いま自分が着手すべき唯一のタスクを即座に取得したい。なぜなら、膨大なタスクリストから次に行うべき作業を判断する思考コストと迷いをゼロにするためだ。
  - 受け入れ基準
    - ［Event-driven］クライアントが引数なしで `get_current_task` ツールを呼び出したとき、システムは未完了の先頭タスク（状態が `in_progress` のタスク、または未着手 `pending` の最前タスク）の情報を返却しなければならない。
    - ［State-driven］すべてのタスクが `completed` となった状態で `get_current_task` が呼び出されたとき、システムは全タスク完了（All Tasks Completed）を示す明示的なレスポンスを返却しなければならない。

- 要件 B-2: シングルアクティブ制約の強制
  - ユーザーストーリー
    - 私はハーネスとして、エージェントが複数のタスクを同時に「進行中」にして作業を散乱させるのを防ぎたい。なぜなら、1つのタスクに集中して完遂させることが品質向上の鍵だからだ。
  - 受け入れ基準
    - ［Event-driven］クライアントが `update_task_status` でタスクの状態を `in_progress` に変更しようとしたとき、システムは他に `in_progress` のタスクが存在しない場合のみ変更を受理しなければならない。
    - ［Unwanted-behavior］既にいずれかのタスクが `in_progress` である状態で、別のタスクを `in_progress` に変更しようとしたとき、システムはエラーを返して要求を拒否しなければならない。

- 要件 B-3: 暗黙的先行依存の強制 & スキップの完全遮断
  - ユーザーストーリー
    - 私はシステム設計者として、先行タスクが終わっていないのに後続タスクを着手・完了扱いにする「タスク飛ばし」を物理的に遮断したい。なぜなら、前工程の成果物なしに後工程を実行しても確実に失敗するためだ。
  - 受け入れ基準
    - ［Unwanted-behavior］インデックス $N$ の先行タスクが `completed` 状態でないとき、インデックス $N+1$ 以降の後続タスクに対して `in_progress` または `completed` への状態変更要求が行われた場合、システムはガードレール違反エラーを返し、状態更新を阻止しなければならない。
    - ［Ubiquitous］システムは、未完了のタスクを飛ばす「スキップ」状態や「スキップ」操作を一切提供してはならない。

- 要件 B-4: 状態遷移のバリデーションと失敗記録
  - ユーザーストーリー
    - 私は AI エージェントとして、タスクの着手・完了・失敗をメモ付きで記録したい。なぜなら、作業履歴を残し、失敗時にも原因をコンテキストにフィードバックするためだ。
  - 受け入れ基準
    - ［Event-driven］クライアントが現在アクティブなタスクに対して `completed` への更新を要求したとき、システムはそのタスクを完了状態に更新し、後続タスクを着手可能としなければならない。
    - ［Event-driven］タスク実行中に問題が発生しクライアントが状態を `failed` と更新メモ（notes）を送信したとき、システムはそのタスクを失敗状態として記録し、エラー履歴を保存しなければならない。

- 要件 B-5: リトライ上限とサーキットブレーカー（実行中断）
  - ユーザーストーリー
    - 私は AI エージェントおよびシステム管理者として、解決困難なタスクでエージェントが無限ループに陥るのを防ぎ、適切にユーザーへ判断を委ねたい。なぜなら、無駄なトークン消費を抑え、人間に早期の修正判断を仰ぐためだ。
  - 受け入れ基準
    - ［Event-driven］クライアントがタスクの状態を `failed` に更新したとき、システムはそのタスクの `retry_count` をインクリメントしなければならない。
    - ［State-driven］タスクの `retry_count` が3未満であるとき、システムはそのタスクの再実行（`in_progress` への再遷移）を許可しなければならない。
    - ［Unwanted-behavior］同一タスクの `retry_count` が3に達したとき、システムはそのタスクを `blocked`（実行中断）とし、さらなる自動再実行要求を拒否して人間による判断待ちメッセージを返却しなければならない。

### 要件カテゴリC: 進捗可視化 & ローカル透過永続化 (Visibility & Persistence)

- 要件 C-1: 全体サマリーと進捗状況の出力
  - ユーザーストーリー
    - 私は開発者および AI エージェントとして、全体の消化状況（何個中何個完了したか）と現在の立ち位置を一目で把握したい。なぜなら、残り作業量と全体進捗を即座に評価するためだ。
  - 受け入れ基準
    - ［Event-driven］クライアントが `get_task_summary` ツールを呼び出したとき、システムは総タスク数、完了タスク数、進捗率（%）、現在アクティブなタスク、および全タスクの順序付きステータス一覧を整形して返却しなければならない。

- 要件 C-2: ローカル JSON 透過永続化とアトミック書き込み
  - ユーザーストーリー
    - 私はプロジェクトの開発者として、エージェントのタスク進行状態が Git で追跡でき、必要に応じてエディタで直接手動修正できるようにしたい。なぜなら、ブラックボックス化を排除し人間がいつでも介入できるようにするためだ。
  - 受け入れ基準
    - ［State-driven］タスクリストの初期化または状態更新が発生したとき、システムはプロジェクトルートの `.agent/tasks.json` に整形された JSON として即座に書き込まなければならない。
    - ［Ubiquitous］システムは、ファイル書き込み時に一時ファイルへの保存後にアトミック置換（Write-Replace）を行い、プロセスクラッシュや電源断時にも `.agent/tasks.json` の破損を防がなければならない。

### 要件カテゴリD: MCP プロトコル & 運用基盤 (MCP Transport & Operations)

- 要件 D-1: stdio JSON-RPC 2.0 準拠
  - ユーザーストーリー
    - 私は MCP クライアントとして、標準的な stdio 経由でタスク管理サーバーと対話したい。なぜなら、追加のネットワーク設定なしに任意のクライアントに組み込めるようにするためだ。
  - 受け入れ基準
    - ［Event-driven］MCP クライアントから標準入力経由で JSON-RPC 2.0 リクエストが送られたとき、システムは仕様に準拠した JSON-RPC レスポンスを標準出力へ返却しなければならない。

- 要件 D-2: stdout 汚染の防止と stderr ロギング
  - ユーザーストーリー
    - 私はシステム開発者として、デバッグログによって MCP の通信プロトコルが破壊される事態を絶対に防止したい。なぜなら、stdout に余計な文字列が1文字でも混ざると JSON-RPC パースエラーでクライアントが切断されるためだ。
  - 受け入れ基準
    - ［Ubiquitous］システムは、トレースやデバッグログなどのすべてのログ出力を標準エラー出力（stderr）にのみ出力し、標準出力（stdout）には純粋な JSON-RPC メッセージ以外を出力してはならない。
